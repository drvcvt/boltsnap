## P1 Standard-Speicherordner aus dem XDG-Bilderordner

**Fix.** Heute (`src/platform/linux/paths.rs:139-141`):
`default_screenshot_dir()` ist fest `~/Bilder/boltsnap`, auch auf
englischen Systemen; `default_save_path()` (`--save`, `:153-160`) ist fest
`~/Pictures/Screenshots/…`. Auf diesem Rechner gibt es `~/Pictures` gar
nicht (`XDG_PICTURES_DIR="$HOME/Bilder"` in `~/.config/user-dirs.dirs`).
Beide sind also für einen Teil der Nutzer falsch, nur verschieden falsch.

Ziel: beide gehen vom Bilderordner des Nutzers aus, wie xdg-user-dirs ihn
festlegt:
- `XDG_PICTURES_DIR` aus `$XDG_CONFIG_HOME/user-dirs.dirs` (sonst
  `~/.config/user-dirs.dirs`), Format `XDG_PICTURES_DIR="$HOME/Bilder"` oder
  ein absoluter Pfad; Kommentare und andere Zeilen werden übersprungen.
- Fehlt die Datei oder der Eintrag, oder ist der Wert weder absolut noch
  `$HOME/…`: `~/Pictures`.
- Shelf-Speichern: `<Bilder>/boltsnap` (bei dir unverändert `~/Bilder/boltsnap`).
- `--save`: `<Bilder>/Screenshots/boltsnap-<ts>.png` (wie bisher, nur mit dem
  richtigen Bilderordner).
- Gilt nur ohne `--save-dir`, `$BOLTSNAP_SAVE_DIR` und `save_dir` in der
  Config (Reihenfolge `src/config.rs:640-654` bleibt). `record_dir` folgt
  `save_dir` wie bisher.

Nicht: keine Umgebungsvariable `XDG_PICTURES_DIR` (die liest auch GLib
nicht), kein Aufruf von `xdg-user-dir`, keine Migration bestehender Dateien,
Windows unverändert (eingefroren, nutzt schon `FOLDERID_Pictures`).

Bau:
1. Split zuerst (eigener Commit, nur Umzug): `paths.rs` hat 547 Zeilen, davon
   173 Zeilen Tests. `paths.rs` → `paths/mod.rs`, Tests nach
   `paths/tests.rs`. `src/platform/linux/` hat danach 10 statt 11 Dateien.
2. `paths/mod.rs`: `fn config_home()` (aus `config_dir()` herausgelöst),
   `fn pictures_dir_in(user_dirs: &str, home: &Path) -> Option<PathBuf>`
   (reine Funktion), `pub fn pictures_dir()`; `default_screenshot_dir()` und
   `default_save_path()` nutzen sie.
3. Doku: Kommentar in `src/config.rs:640`, `docs/guide/configuration.md:8-9`
   („Default: your pictures folder, e.g. ~/Pictures/boltsnap“).

Was brechen kann: wer heute ohne Config auf einem englischen System
speichert, bekommt künftig `~/Pictures/boltsnap` statt `~/Bilder/boltsnap`
(das ist der Fix; alte Dateien bleiben liegen). Tests in
`src/config/tests.rs:384-395` vergleichen mit `default_screenshot_dir()`
und bleiben gültig.

Test: `pictures_dir_in` mit `$HOME/Bilder`, absolutem Pfad, Kommentarzeile,
fehlendem Eintrag, relativem Wert (→ `None`), Anführungszeichen fehlen.
Abnahme: `cargo test`, und `boltsnap doctor` zeigt hier weiter
`~/Bilder/boltsnap`, falls doctor den Ordner zeigt (sonst ein Testlauf von
`pictures_dir()` mit der echten Datei).

## P2 Icon-only-Controls in der schmalen Spalte mittig

**Fix, reproduziert** (`selector_shots`, Desktop-Schrift, 02.11.):
„140x240 on false: icon-only control's icon off its middle by -0.62,
+0.00“; dieselbe Spalte mit `on true` 0,50 (genau an der Grenze), alle
anderen Anordnungen ≤ 0,12.

Ursache: In Anordnung 3 (`[Record] / [Clip] / [Frame, Audio]`,
`src/selector/render/toolbar.rs:91-96`) streckt `justify` (`:240-263`)
Frame und Audio auf die Zeilenbreite, in ganzen Pixeln mit dem Rest am
letzten. Ist eine gestreckte Breite minus `ICON_BOX` ungerade, setzt
`icon_rect` (`:408-421`) das Icon mit `floor` einen halben Pixel links der
Mitte; dazu kommt die eigene Asymmetrie des Aus-Icons (−0,12). Ob das
passiert, hängt an der Breite von „Record“/„Clip“, also an der Schrift; mit
der eingebetteten Schrift der Unit-Tests zufällig nicht.

Ziel: Die Breite der Toolbar wird so gewählt, dass jede Zeile nur aus
Icon-only-Controls sich in gerade Anteile teilt: `extent` gibt bis zu
`2·n − 1` px mehr Breite, bis der Rest dieser Zeile ein Vielfaches von
`2·n` ist. Dann ist jede gestreckte Breite `CTL + gerade`, `CTL − ICON_BOX`
= 12 ist gerade, das Icon sitzt exakt mittig auf ganzen Pixeln. Die
Zeilen mit Labels nehmen die zusätzlichen Pixel wie heute schon auf (Text
steht am Anfang, Rand bleibt rundum gleich).

Entscheidung: Breite runden (statt `ceil` in `icon_rect`: verschiebt den
Fehler nur nach rechts, +0,5 bleibt; statt das Icon auf halbe Pixel zu
setzen: verletzt das Pixelraster, die Striche verschmieren).

Nicht: keine Änderung an einzeiligen Anordnungen, an Abständen oder an
Icons; die Toolbar wird in Anordnung 3 höchstens 3 px breiter.

Bau: `toolbar.rs` `extent` (oder ein Schritt direkt danach in `layout`,
damit die Passprüfung dieselbe Breite sieht). Test in
`src/selector/render/tests.rs` (398 Zeilen, `chrome_tests.rs` hat schon
589): für Label-Breiten über einen Bereich mit Bruchteilen (Metrics mit
`#[cfg(test)]`-Konstruktor) liegt in Anordnung 3 die Mitte jedes
`icon_rect` der Icon-only-Controls exakt auf der Control-Mitte, und alle
Zeilen enden am rechten Rand. Schlägt vor dem Fix fehl.

Abnahme: `selector_shots` mit der Desktop-Schrift läuft durch (alle Gates
grün, Zahlen im Bericht), `cargo test`.

**Abweichung (beim Bau):** Mit dem Fix hätte `toolbar.rs` 510 Zeilen gehabt.
Deshalb wird es zuerst aufgeteilt, als eigener Commit und nur als Umzug:
- `render/toolbar/mod.rs` (217 Zeilen): Konstanten, Look, Farben,
  `icon_rect`, Zeichnen.
- `render/toolbar/layout.rs`: Anordnungen, `Metrics`, `Layout`, `layout`,
  wieder exportiert, damit die Pfade gleich bleiben.

Der Fix (`centred_icons`) und sein Test landen in `layout.rs`, nicht in
`render/tests.rs`, weil der Test an die privaten `Metrics`-Felder muss.

## P3 Selector schneller sichtbar

**Befund (gemessen).** Live (01.11., 10 Läufe `boltsnap area`,
`BOLTSNAP_TIMINGS`): Aufnahme ~17 ms, erster Frame bei ~51 ms; die
Layer-Surfaces entstehen erst nach dem Join der Aufnahme
(`src/platform/linux/select_skia/mod.rs:221-305`), im Configure-Handler
(`:740-756`) dann Basis und `SceneCache::new` einthreadig, ~27 ms.

Headless (02.11., Wegwerf-Probe, 3840 × 1080, Release):

| Schritt | warm | erster Lauf |
| --- | ---: | ---: |
| `base_pixmap_from_image` (Kopie 16 MB) | 1,4–1,6 ms | 2,1 ms |
| `SceneCache::new` → `CachedOverlay::new`: Klon, Abdunkeln mit tiny-skia `fill_rect`, zweiter Klon | 10,8–13 ms | 15,0 ms |
| erstes `update` (ganzer Frame: `dimmed` → `frame` kopiert, obwohl gleich) | 1,5–1,9 ms | 1,5 ms |
| `copy_viewport` in zwei 1080p-Buffer | 2,0 ms | 2,1 ms |
| Summe | ~16 ms | 20,7 ms |

**Ziel:** erster Commit (`selector_first_commit`) bei etwa 30 ms statt ~51
ms (Schätzung), **Pixel identisch** zu heute.

Verhalten bleibt: dieselben Bilder, dieselbe Prüfung, dass die eingefrorenen
Pixel zur aktuellen Monitor-Anordnung passen (sonst derselbe Fehler wie
heute), Aufnahme-Modus unverändert.

**P3a Zerlegen (eigener Commit, keine Verhaltensänderung).**
`select_skia/mod.rs` hat 790 Zeilen, `run_selector` ~270. Aufteilung:
- `select_skia/startup.rs` (neu): `Selector::new` (das Struct-Literal, die
  vier Schalter als `Start { instant, record_mode, show_frame,
  audio_enabled }`), die Monitorwahl für Aufnahme- und Screenshot-Modus
  (`record_output`, `capture_outputs`), das Anlegen der Layer-Surfaces
  (`open_view`), die Replay-Vorschau-Quelle (`watch_replay_preview`).
- `select_skia/wayland.rs` (neu): `OutputHandler`, `LayerShellHandler`
  (Configure), `ShmHandler`, `ProvidesRegistryState`, `delegate_*`.
- `mod.rs` behält Typen, Einstiegspunkte, `run_selector` als Folge
  benannter Schritte, `Selector` und seine Methoden; Ziel ≤ 500 Zeilen.
  `select_skia/` hat danach 7 Dateien.

**P3b Schneller.**
1. Abdunkeln ohne tiny-skia im heißen Weg: `CachedOverlay::new` baut
   `dimmed` in einem Durchgang aus `base` über zwei 256er-Tabellen (Farbe,
   Alpha), die **tiny-skia selbst** einmal erzeugt (ein 256 × 1-Pixmap mit
   `(i, i, i, i)`, darüber derselbe `fill_rect`). Zeilenbänder auf bis zu 4
   Threads (`std::thread::scope`), `frame` als Kopie davon.
   `dim_and_restore_with_style` bleibt für Auswahl und Windows.
2. `CachedOverlay` merkt sich, dass `frame` noch gleich `dimmed` ist; das
   erste `reset_regions` kopiert dann nur die Auswahl, nicht 16 MB.
3. Screenshot-Modus: die Layer-Surfaces gleich nach dem ersten Roundtrip
   für alle Outputs anlegen, während die Aufnahme noch läuft (ohne Buffer
   unsichtbar). Nach dem Join: jeden eingefangenen Monitor seinem View per
   Name zuordnen, Viewport setzen, Reihenfolge wie die Aufnahme; Views ohne
   Monitor werden zerstört; Monitor ohne View → „capture monitor
   disconnected“ wie heute; danach dieselbe `target_layout_valid`-Prüfung.
   Das Configure liegt dann schon in der Warteschlange, wenn die Basis
   fertig ist.
4. Basis und Overlay direkt nach dem Join bauen statt im Configure-Handler
   (der baut nur noch, wenn die Größe abweicht, wie heute).

Was brechen kann: Reihenfolge Views ↔ `captured_monitors` (Index-Abgleich in
`target_layout_valid`, `:583-597`), deshalb Zuordnung per Name vor jeder
Prüfung; Tastatur-Fokus geht schon während der Aufnahme an die (unsichtbare)
Surface (Esc in diesen ~17 ms bricht ab statt verloren zu gehen);
Pixelgleichheit der Tabelle bei nicht deckenden Pixeln (Aufnahme-Modus nutzt
`transparent_base`): der Test deckt alle `(c, a)` mit `c ≤ a` ab; Threads im
geteilten Code sind plattformneutral (std).

Tests: `dimmed` aus der Tabelle gleich dem alten Weg (Toleranz 0) für ein
zufälliges Bild mit Alpha und für das volle `(c, a)`-Raster; das erste
`reset_regions` nach `new` liefert dasselbe wie vorher; Zuordnung
Monitor ↔ View als reine Funktion (vertauschte Reihenfolge, fehlender und
zusätzlicher Output).

Abnahme: Probe headless vorher/nachher (Zahlen hier); live 10 Läufe
`boltsnap area` mit `BOLTSNAP_TIMINGS` (`process_entry` →
`selector_first_commit`) **nur nach Zustimmung** (öffnet den Selector auf dem
Desktop, Regel „keine Desktop-Proben ungefragt“).

## P4 release.yml absichern

**Befund** (`.github/workflows/release.yml`):
- Dritt-Actions auf beweglichen Tags: `dtolnay/rust-toolchain@stable`,
  `Swatinem/rust-cache@v2`, `softprops/action-gh-release@v2`;
  `actions/checkout@v4` ebenso nur als Tag.
- Veröffentlicht sofort (kein Entwurf), `contents: write` für den ganzen Job.
- **Bug:** von Hand gestartet (`workflow_dispatch` mit `tag`) baut sie den
  Stand des Branches, auf dem sie läuft, und nennt ihn nach dem Tag.
- `cargo install cargo-deb` ohne Version.
- Kein Abgleich, dass der Tag auf `main` liegt und zur Version in
  `Cargo.toml` passt.

Ziel (Versionsregel, `2026-10-28-updater.md` „Sicherheitsmodell“):
- Nur `actions/checkout`, auf Commit-SHA (v7.0.1 =
  `3d3c42e5aac5ba805825da76410c181273ba90b1`, über die GitHub-API
  nachgesehen), `persist-credentials: false`, ganzer Verlauf.
- Rust per vorinstalliertem `rustup` (Version fest auf 1.98.1, die lokale),
  kein Cache.
- `cargo install --locked cargo-deb@3.8.0`.
- Prüfungen vor dem Bau: Tag hat die Form `vX.Y.Z`, entspricht
  `version` in `Cargo.toml`, und der Commit liegt auf `origin/main`.
- Von Hand: baut genau den angegebenen Tag (Checkout `ref`).
- Am Ende `gh release create "$TAG" --draft --verify-tag --generate-notes`
  mit den Dateien; veröffentlichen tut der Nutzer.
- `permissions: contents: write` nur da, wo es gebraucht wird (ein Job, also
  auf Job-Ebene, oben `{}`).
- `ubuntu-22.04` bleibt: ältere glibc, das Binary läuft auf mehr Systemen.

Nicht: kein Updater-Manifest, keine Signatur, keine Attestation (U1/U2 im
Updater-Plan, geparkt), keine weiteren Binaries im Paket, kein Tag, kein
Release. `ci.yml` bleibt in GitHub abgeschaltet (`disabled_manually`).

Abnahme: `actionlint` falls vorhanden, sonst YAML-Parse und die
Shell-Schritte lokal mit `shellcheck`/`sh -n`; der echte Lauf ist erst der
Release-Tag (er legt nur einen Entwurf an, also ist ein Fehler dort nicht
öffentlich). Das steht offen im Bericht.
